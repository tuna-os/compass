# ADR-0016: Screen-reader gap — Orca cannot see the Rust launcher

**Status:** Accepted, amended by [ADR-0018](./0018-the-open-calls-decided.md) — screen-reader users keep the C++ engine until the tree exists, and Phase 8 waits for it — and by [ADR-0022](./0022-the-november-calls-decided.md), which picks AccessKit's Unix adapter as the route to the tree. The tree now exists (#302–#304, see [Where it stands](#where-it-stands-2026-11-05)); the gap that remains is the Orca gate, #305 · **Date:** 2026-09-21 · Relates to: #118, #10, ADR-0001 · Re-visits: PLAN.md §6 Phase 7

## Context

The Rust launcher (`iced` 0.14 + `winit` 0.30) has no accessibility tree. Neither
crate depends on `accesskit`, and `Cargo.lock` contains zero occurrences of
`accesskit`, `atspi` or any AT-SPI binding. Orca (GNOME's default screen
reader) therefore sees nothing: not the query field, not the result list, not
the selection, not the action panel. The launcher is bound to **Super+Space** —
intended as the fastest path to anything on the system — and for a blind user
it is currently the one path they cannot use at all.

This was found while answering #4's “watch for” clause; see #118 and #116. Qt's
`QAccessible` gives the C++ engine AT-SPI, so the gap is a **regression the
cutover would ship**, not a pre-existing absence.

## Decision

**Accepted gap for cutover, documented explicitly** — option 4 in #118:

1. Cutover (Phase 7, #10) ships Linux with the Rust engine as default while
   noting the gap plainly in the release notes.
2. The decision is revisited under Phase 9/10 or when Iced gains AccessKit
   integration (the natural home for `winit`-based toolkits). Options 1–3 in
   #118 (wait upstream, contribute upstream, or implement AT-SPI ourselves)
   remain open and are not chosen now because the cost/owner tradeoff is not
   decidable without a survey of Iced's AccessKit effort and a check of what
   the C++ engine actually exposes today.

## Consequences

- One full release cycle with no P0 regressions remains the Phase 7 gate, but
  “P0” does not include a11y until the tree exists — the gap is not a
  regression to be filed after cutover, it is a known absence to be stated
  before.
- If a user has Orca enabled, `doctor` should surface the absence as a
  supported degradation (warning, not failure) rather than silence.
- Any change that adds `accesskit`/`atspi` to the workspace must be accompanied
  by an update to this ADR. When the tree arrived (below), the sentinel that
  enforced the absence became `crates/compass-ui/tests/a11y_gap.rs`'s
  `adr_0016_records_the_tree_and_what_is_still_open` and
  `the_adapter_is_in_the_lock`, which keep what is still open recorded.

## Where it stands (2026-11-05)

The Context above is the state #118 found, kept as history. Since ADR-0022 §1 the launcher has a
tree:

- **The description.** `compass-ui` describes the window from its state, not from Iced's widgets
  (`compass_ui::semantics`, built by `LauncherApp::semantics`): a `Window` named Compass; the search
  field as an editable `SearchInput` with its text, placeholder and caret; the results as a
  `ListBox` of `ListBoxOption`s with name, description, position, count and selection; a polite
  live `Status` for "Type to search", "No results", "Loading…", the result count once something is
  typed, and errors; the action panel as a `Menu` of `MenuItem`s with their section, shortcut and
  current item; the confirmations as an `AlertDialog` with the keys that answer them; and the
  preference, argument and extension forms as a `Form` of text, password, multi-line, checkbox,
  combo box, tag list, file button and note controls, with label, value, required and invalid
  states. A password is exposed as bullets, never as itself. The focus is reported on the field
  while the person types and on the selected result once they move through the results (the
  keyboard itself never leaves the field); the open panel, a dialog and a form's current field take
  it while they are there.
- **The adapter.** `compass-a11y-linux` (`AtspiTree`) serves that tree on AT-SPI through
  `accesskit_unix`. It is created when the launcher window opens and dropped when it closes, so a
  hidden launcher leaves no nodes on the bus, and it exports nothing until assistive technology
  turns accessibility on. `compass_platform::AccessibilityTree` is the seam; AccessKit's macOS and
  Windows adapters would be other implementations of it.
- **Requests.** A click on a result or a panel action, focus on a result, a panel action, the search
  field or a preference form's field, setting the search text or a single-line text field, and
  ticking a checkbox all come back to the window as `Message::Accessibility` and do what the
  keyboard or a click would. Only the requests that do something are advertised.
- **Tests.** The description is unit-tested without a display (`semantics`, `app::a11y`), and
  `crates/compass-a11y-linux/tests/private_bus.rs` reads the tree back off a private accessibility
  bus with the AT-SPI client proxies: the window, the field's text, the results and selection, a
  selection change, a press reaching the launcher, and nothing left after the window closes.

**Still open, and why `doctor` still warns:**

- No Orca session has read the launcher yet. That is #305's gate (a tier-2 or tier-3 session and a
  manual Orca checklist on Bluefin); until it passes, `doctor` keeps warning a screen-reader user
  and the `a11y_gap` test keeps this section honest.
- Most builtin views (clipboard history, the emoji picker, the window switcher, the settings, and
  the others with their own lists) describe their search field and nothing under it. The root
  search, extension lists, forms and alerts, the preference and argument forms, the action panel
  and the confirmations are described. Extension Detail views are not.
- Child bounds are not reported, so a screen reader's flat review cannot place the nodes on
  screen. Wayland does not give a window its position in any case.
